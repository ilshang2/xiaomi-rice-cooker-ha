# 食譜（`cooking-data`）封包格式

[English](recipe-format.md) | **繁體中文**

米家電子鍋 mini（`chunmi.cooker.tw1`）如何編碼食譜、如何在 Home Assistant 裡**經區網本地**送出（不經小米雲端），
以及還沒解開的部分。

## 怎麼找到的

1. 在 root 的手機上執行米家 App（小米官方大陸版 11.9.x），用 Frida 掛在外掛的原生橋接。按下「開始」的瞬間，
   App 會用一個字串參數呼叫 MIoT 動作 `siid 4 / aiid 1（set-start）`：這個字串就是下面的封包，而且是明文。
2. 電鍋外掛（`mijia.chunmi.cooker.tw1`，純文字的 React Native bundle）裡有編輯封包表頭的類別
   （`CMCookProfile`），表頭每個欄位因此都有名字。
3. App **沒有加熱曲線的編碼器**。完整封包（含曲線）來自雲端的食譜資料；App 只改表頭並重算 CRC。

## 封包格式（176 位元組）

| 位元組 | 內容 |
|---|---|
| 0–19 | 表頭（見下） |
| 20–173 | 加熱曲線（見「尚未解開」） |
| 174–175 | 前 174 位元組的 CRC-16/XMODEM（多項式 0x1021、初值 0、不反轉、xorout 0），**大端** |

### 表頭

| 索引 | 欄位 |
|---|---|
| 0、1 | 裝置類型、小類型（`02 01`） |
| 2 | *index*：模式 1–4 保留原值（00–03）；食譜編號 > 4 時，App 立即開始用 `05`、存入收藏用 `04` |
| 3–6 | menu id，32 位元大端，即食譜編號（見下） |
| 7 | 旗標：bit7 自訂儲存、bit6 可預約、bit5 可設自動保溫。低 5 位元電鍋不理會 |
| 8、9 | 烹飪時間：時、分 |
| 10、11／12、13 | 時長上限／下限（時、分）。上限 > 下限才可調整 |
| 14 | bit7＝預約開關，低 7 位元＝幾小時後開始 |
| 15 | bit7＝自動保溫，低 7 位元＝再幾分鐘後開始 |
| 17、18 | 米種 id（16 位元） |
| 19 | 口味（軟硬） |

### 食譜編號（`data/recipes.json`）

| id | 食譜 | id | 食譜 |
|---|---|---|---|
| 01 | 精煮飯 | 09 | 蛋糕 |
| 02 | 快煮飯 | 0a | 煲湯 |
| 03 | 煮粥 | 0b | 再加熱 |
| 04 | 保溫 | 0c | 關東煮 |
| 05 | 燉煮 | 0d | 熱米飯 |
| 06 | **優格** | 0e | 香甜煮 |
| 07 | 嬰兒粥 | 0f | 極速煮 |
| 08 | 泡麵 | | |

## 從 Home Assistant 送出食譜

```yaml
service: xiaomi_miot.call_action
data:
  entity_id: sensor.chunmi_tw1_c3d7_cooker   # 你的電鍋
  siid: 4
  aiid: 1
  params: ["<176 位元組封包，352 個十六進位字元>"]
```

`tools/cookcode.py` 會組封包（改表頭並重算 CRC）：

```
python tools/cookcode.py list
python tools/cookcode.py show 優格
python tools/cookcode.py hex 優格 --minutes 360 --keep-warm off
python tools/cookcode.py hex 燉煮 --minutes 90 --order 60      # 60 分鐘後開始
```

卡片的**食譜**分頁在瀏覽器裡做同樣的事（JavaScript 版本，已與 Python 工具逐位元組比對）。
停止用 `button.…_cancel_cooking`。

真機驗證：原版封包會啟動對應食譜；改時長有效（優格設 300 分鐘 → `t_cook` 300）；精煮飯預約 3 分鐘 →
`t_pre` 3；表頭第 7 位元組不被檢查。

> **送出封包會立刻開始加熱。** 請確認內鍋有水或食材。

## 加熱曲線（部分解開）

第 20–173 位元組是加熱曲線：從第 26 位元組起是一張 7 位元組一筆的**階段記錄表**
`91 b1 b2 78 b4 b5 b6`（第 *i* 筆從 `26 + 7*i` 開始），部分食譜後面還有 14 位元組一塊的第二張表。
電鍋的 `phase`（階段，siid 4、piid 18）就是記錄索引。優格曲線的第 0 筆（`... 00 1e 00`）是 30 秒等待，
電鍋也確實在階段 0 停約 30 秒。

在真機上的實測（優格曲線、階段 1、1 公升室溫水起跑）：

| 欄位 | 意義 | 證據 |
|---|---|---|
| **`b2`** | **該階段的目標溫度（°C）** | `29`（41 °C）：加熱到約 44 °C 就停、讀數回降；改成 `37`（55 °C）：一路加熱越過 44 °C，直到 54 °C 的安全停止點 |
| **`b4`** | **加熱功率等級** | `03`：約 +0.3 °C/分；`10`：+2.1 °C/分；`20`：+5～7 °C/分；`40`：約 +5.6 °C/分（與 `20` 接近，可能在 `20` 附近就飽和）；`08`：在 67 °C 時只勉強勝過散熱 |
| `b1` | 不是功率。在第 3 筆會改變階段 3 的進入／跳過（`20`、`2b`、`ff` 被跳過），但不影響升溫速率 | 未解 |
| `b5`、`b6`、`78`、第二張表 | 未知 | 未解 |

多數記錄裡填的 `7d`（125）、`6e`（110）、`82`（130）、`78`（120）看起來是「不設限」的溫度預設值。
這些結論來自優格階段 1 與幾次泡麵實驗；其他階段推定用同樣的欄位，尚未逐一驗證。

重現實驗的提醒：`temp`（siid 4、piid 30）是內鍋底下的熱敏電阻。全力加熱時讀數會比水溫高 3 °C 以上，剛加冷水時
更是不準。請先等讀數穩定，並比較趨勢，不要看單一讀數。要即時讀取請用 `xiaomi_miot.get_properties`（約 0.2 秒），
不要等 HA 感測器更新。

`tools/cookcode.py` 可以改某階段的目標溫度與功率（`--phase 1 --target 45 --power 16`），範圍限制在
30–95 °C、功率 <= 0x40。**這是實驗功能**：它只改一條我們還沒完全弄懂的曲線裡的兩個欄位。第一次請在鍋裡有水、
人在旁邊的情況下觀察。

## 自訂恆溫食譜

優格流程會維持恆溫，所以拿它當自訂恆溫的底：階段 1（第 33 位元組起，`b2` 在 35、`b4` 在 37）與階段 8
（第 82 位元組起，`b2` 在 84、`b4` 在 86）設成同一組目標溫度與功率，表頭時間就是恆溫時間，預約與自動保溫位元清掉。
`python tools/cookcode.py hold --hold 65 --minutes 90` 可產生封包（30–90 °C、1–1440 分、功率 8–64）。

長時間實測（優格流程、目標 75 °C）：**階段 1 約 30 分鐘，之後電鍋換到階段 8**；階段 8 若維持預設的 40 °C，
鍋子會慢慢降溫（60 分鐘內 77 → 63 °C），所以兩筆都要設（階段 8 同溫的長時間效果尚未實測）。多段串接由卡片／`script.cooker_program` 負責：
取消、等待機、送下一個封包（電鍋忙碌時送的封包會被忽略）。已在真機以 2 段各 2 分鐘（50 °C 再 60 °C）驗證。

冷水起跑實測（1 公升室溫水、目標 50 °C、功率 32、18 分鐘）：前 1 分鐘讀數 42～44 °C（冷水加上鍋底餘溫），約 3 分鐘到 50 °C，之後維持 50～54 °C，最高 54 °C，沒有失控過衝。感測器讀數會比實際水溫高約 2～4 °C。

## 法律／倫理

這是對作者自己擁有的裝置所做的互通性研究。`data/recipes.json` 內的封包是小米為這台電鍋提供的食譜資料，
收錄只為了能在本地控制電鍋；不含任何小米程式碼。與小米無關。
